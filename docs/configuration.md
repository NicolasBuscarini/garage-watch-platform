# Configuração e desenvolvimento

## Orçamento de recursos

O entrypoint `./garage` injeta limites Compose configuráveis: `PLATFORM_API_CPUS`/`PLATFORM_API_MEMORY_LIMIT` (2 CPUs/3 GiB), `PLATFORM_TEST_CPUS`/`PLATFORM_TEST_MEMORY_LIMIT` (2 CPUs/3 GiB) e `PLATFORM_WEB_CPUS`/`PLATFORM_WEB_MEMORY_LIMIT` (1 CPU/1 GiB). São tetos cgroup, não reservas nem garantias de desempenho; ajuste ao host. Valem após criar/recriar o container. Não recrie API durante captura sem janela operacional autorizada.

Detector ONNX: `DETECTOR_INTRA_OP_THREADS` (1–8, default 1), `DETECTOR_INTER_OP_THREADS` (1–4, default 1) e `DETECTOR_SAMPLE_EVERY_SEGMENTS` (1–120, default 1) controlam paralelismo e frequência de amostragem. A amostragem ignora segmentos intermediários sem bloquear captura; fila permanece limitada e descarte explícito. A raiz projeta os equivalentes `PLATFORM_DETECTOR_*` via `./garage`.

O ambiente de desenvolvimento deve ser executado via Docker Compose. Copie `.env.example` para `.env` e ajuste `APP_UID`, `APP_GID` aos IDs do usuário local e `APP_PORT` se necessário. O `.env` é ignorado. O serviço é publicado somente no loopback (`127.0.0.1`), usa imagem oficial .NET SDK `10.0.403` por digest, FFmpeg Ubuntu `7:6.1.1-3ubuntu5`, usuário não-root, `no-new-privileges`, capacidades removidas e tmpfs limitado. O spool T02 é persistido no bind mount local ignorado `./data`; nenhum segredo de produto é versionado. Pull da imagem, restore e pacotes do sistema dependem de MCR/NuGet/Ubuntu archives. NuGet usa lockfiles/hash; o pacote FFmpeg está fixo por versão Debian, mas suas dependências de sistema vêm do repositório Ubuntu sem snapshot imutável. Esse tráfego é de ferramentas/pacotes, não de mídia/pessoas.

Os lockfiles `packages.lock.json` estão versionados. Comandos: `docker compose build`; restore travado `docker compose run --rm api dotnet restore GarageWatch.slnx --locked-mode`; teste `docker compose --profile test run --rm test`; execução `docker compose up --build`. Ao alterar dependências, atualizar e revisar lockfiles explicitamente antes do commit. Nenhuma instalação de SDK no host nem acesso à câmera/NAS é necessário. API usa cache NuGet temporário em tmpfs limitado a 1 GiB; o container `test` usa até 1 GiB. Esses limites evitam que o cache cresça sem controle, mas tmpfs consome memória do host/cgroup conforme usado. Nenhum pacote é persistido em mídia/dados da aplicação. Todo ambiente é injetado; não adicionar connection strings, tokens ou senha ao Compose.

Variáveis: `APP_PORT` (8081 padrão), `APP_UID`/`APP_GID` (1000 padrão), `IDENTITY_DB_PATH` (arquivo SQLite absoluto; Compose usa `/data/identity/garagewatch.db`), `AUTH_USERNAME`/`AUTH_PASSWORD` (bootstrap somente quando o banco não possui contas; mínimo 6 caracteres, sem classes obrigatórias (senha numérica é permitida)), `AUTH_EMAIL` (e-mail opcional do primeiro administrador, ainda sem fluxo de verificação/notificação), `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_HEADERS` e variáveis T02 em `capture.md`. O placeholder do exemplo é rejeitado. Bootstrap sempre cria Administrator; `AUTH_ROLE` não é mais usado. Alterar variáveis depois que existe usuário não troca identidade/credencial. SQLite é a fonte durável de usuário/roles/grants/auditoria; migrations rodam antes do tráfego, falha interrompe startup. No Linux, diretório/banco têm modos 0700/0600; banco fica no volume ignorado `data/`, sem backup/restore coberto nesta tarefa. ASP.NET Core Identity usa hash padrão versionado, lockout após cinco falhas por 15 min e aceita senha mínima de 6 caracteres sem composição obrigatória; rate limiter de login limita cinco tentativas/minuto e cadastro três tentativas/minuto, ambos globais no processo; cadastro ainda valida Origin same-origin. O cookie dura 8 h, não desliza, é HttpOnly/SameSite Strict; SecurityStamp é validado a cada 15 s no máximo e mudanças IAM o atualizam; Data Protection key segue efêmera e restart revoga sessões. Perfil exclusivamente dev/loopback, sem LAN/TLS/keyring durável. T03-REG cria conta User local sem e-mail, verificação, recovery ou grant; o painel mostra landing sem câmera. Cadastro não é permitido como política LAN/produção. Gestão administrativa de contas/grants e pedidos de acesso continuam sem UI; enforcement de grants por mídia segue incompleto. Presença, player e limites OTLP seguem como descritos adiante; sem alegações de latência/CPU homologadas.

`CAPTURE_SEGMENT_TIMEOUT_SECONDS` controla watchdog do T02: `0` usa derivação segura por intervalo de segmento (padrão de 5 s resulta em 20 s); valor configurado deve exceder `CAPTURE_SEGMENT_SECONDS` e não ultrapassar 300 s. `CAPTURE_RTSP_URL` deve permanecer vazio no serviço padrão sintético; para o profile Compose `camera-integration`, `CAMERA_RTSP_URL` é a entrada de interpolação que o profile injeta em `CAPTURE_RTSP_URL`. O cache SDK/NuGet da API usa tmpfs de 1 GiB; o test harness também tem limite de 1 GiB. Pacotes não ficam no volume da aplicação.

**Incidente operacional (31/10/2026):** após rebuild, `api-camera-integration` falhou repetidamente no restore com `NuGet.targets: No space left on device`, embora os filesystems host e HDD tivessem espaço e inodes disponíveis. A API guardava `NUGET_PACKAGES=/tmp/nuget` em tmpfs limitado a 512 MiB. O limite da API foi aumentado para 1 GiB; requer nova tentativa de inicialização para verificar a correção. Nenhum dado aponta falta de espaço no HDD de captura.

O gatilho T04A tem configuração habilitado/desabilitado persistida individualmente por câmera no SQLite IAM, alterável por Administrator em Clipes; o padrão é desligado e a aplicação acontece no processamento do próximo segmento, sem reiniciar captura. `CLIP_TRIGGER_ENABLED` legado não controla a execução do worker. Os parâmetros técnicos continuam por instalação: `CLIP_TRIGGER_SAMPLE_FPS` (1–5), `CLIP_TRIGGER_WIDTH` (64–320), `CLIP_TRIGGER_HEIGHT` (64–180), `CLIP_TRIGGER_PIXEL_DELTA` (1–255), `CLIP_TRIGGER_CHANGED_AREA_RATIO` e `CLIP_TRIGGER_GLOBAL_CHANGED_AREA_RATIO` (>0–1), `CLIP_TRIGGER_ZONE` (`x,y,largura,altura` normalizados), `CLIP_TRIGGER_MASKS` (retângulos normalizados separados por `;`), `CLIP_TRIGGER_COOLDOWN_SECONDS` (0–3600), `CLIP_PRE_EVENT_SECONDS`/`CLIP_POST_EVENT_SECONDS` (0–120), `CLIP_MAX_SECONDS` (1–600) e `CLIP_TRIGGER_QUEUE_CAPACITY` (1–64). O `./garage` projeta os equivalentes `PLATFORM_CLIP_*` da raiz, adicionando defaults seguros a `.env` existente sem tocar em segredos. Somente a câmera atualmente consumida pelo worker consegue gerar clipes; multicâmera ativa permanece dependente de T15-MCAM-RUN. Estes limites não representam suporte, qualidade ou desempenho em câmera real.

T04 detector opcional: `DETECTOR_ONNX_MODEL_PATH` deve ser caminho absoluto para artefato ONNX fornecido externamente; vazio mantém inferência desativada. `DETECTOR_MODEL_VERSION`, nomes `DETECTOR_ONNX_INPUT_NAME`/`DETECTOR_ONNX_OUTPUT_NAME`, dimensões `DETECTOR_INPUT_WIDTH`/`DETECTOR_INPUT_HEIGHT` (32–2048), `DETECTOR_SCORE_THRESHOLD` (0–1), `DETECTOR_LABELS` (CSV) e `DETECTOR_QUEUE_CAPACITY` (1–64) configuram contrato v1. Entrada é RGB float NCHW em [0,1]; saída são linhas `[x1,y1,x2,y2,score,classId]` em coordenadas normalizadas, máximo de 10.000 linhas e 256 detecções aceitas. O worker amostra um frame por segmento, timeout de decode 500 ms, fila limitada e descarte quando cheia; runtime CPU limita threads intra/inter-op a 1. É baseline dev-only, não perfil de produção. Não adapta automaticamente YOLO/Ultralytics ou pré-processamentos específicos. Tracker IoU mantém IDs dentro de câmera+epoch e expira após 10 frames ausentes. Não há pesos/modelo incluídos, confiança calibrada, análise de clipes, retenção de frames ou promoção automática.

T05 recebe regras opcionais por `EVENT_RULES_FILE` (caminho absoluto para JSON `event-rules.v1`; vazio desativa o motor e não emite eventos). O arquivo fixa `configVersion`, `contextId`, `cameraId` e regras imutáveis com versão, classe/score, nível, cooldown e intervalo máximo entre observações. Polígonos/linhas usam coordenadas normalizadas; o ponto de rastreamento é o centro da caixa. Tipos iniciais: permanência em zona e cruzamento direcional de linha. Ocorrências JSON append-only ficam em `<CAPTURE_SPOOL_DIRECTORY>/events`, envelopadas com SHA-256 e IDs determinísticos; `EVENT_JOURNAL_MAX_EVENTS` (padrão 10.000) e `EVENT_JOURNAL_MAX_BYTES` (padrão 64 MiB) limitam o journal, sem política de expurgo. Journal inválido/cheio não bloqueia captura, mas pode descartar eventos e é sinalizado em log/métrica. Estado temporal é volátil e recomeça em restart/configuração nova; IDs/deduplicação de journal persistem. Regras e eventos são dev-only; nenhum nível/limiar de alerta foi calibrado para cena real.

T06 arquivamento local dev-only: `CLIP_ARCHIVE_DIRECTORY` define destino absoluto separado do spool (vazio desativa); via `./garage`, o destino interno do container é `/archive-data`, **não é NAS**. `CLIP_ARCHIVE_POLL_SECONDS` (1–60, padrão 2), `CLIP_ARCHIVE_MAX_CLIPS` (10–100.000, padrão 10.000), `CLIP_ARCHIVE_MAX_BYTES` (1 MiB–1 TiB, padrão 50 GiB) e `CLIP_ARCHIVE_MAX_CLIP_BYTES` (1 MiB–10 GiB, padrão 1 GiB) limitam varredura e cópia. O manifesto do clipe é o registro durável do job; apenas um item é copiado por vez. Conteúdo de mídia, thumbnail e manifesto de commit são copiados/verificados por SHA-256 antes do estado `archived`; originais não são removidos. Retentativas transitórias usam backoff exponencial limitado a 8 tentativas; corrupção/contrato inválido marca `failed`. A cota cheia mantém `retry_wait`; liberar espaço permite nova tentativa. Não há política de expurgo, API de retry nem confirmação de NAS/mount remoto nesta tarefa.

O spool completo da Platform (segmentos, manifests, gaps, clipes e eventos) usa `CAPTURE_DATA_HOST_DIR` como origem de bind no host e `/capture-data` dentro do container. O arquivo T06 usa `CLIP_ARCHIVE_HOST_DIR` no host e `/archive-data` no container. Pela raiz, configure `PLATFORM_CAPTURE_HOST_DIR` e `PLATFORM_ARCHIVE_HOST_DIR`; defaults permanecem `./data/capture` e `./data/archive`, enquanto `/data/identity` continua no armazenamento local existente. Para disco montado, configure `PLATFORM_STORAGE_MOUNT` e, recomendado, `PLATFORM_STORAGE_UUID` no `.env` raiz. `./garage prepare-storage` valida mountpoint/UUID, exige diretórios sob o filesystem escolhido e os cria sem iniciar/parar serviço; `./garage up`, `./garage camera` e `./garage verify-config` recusam se o volume não estiver montado corretamente, evitando fallback silencioso ao SSD. Alterações de bind só afetam a Platform na próxima recriação; dados existentes não são movidos nem apagados por essa configuração.

T04B-API configura o backlog/lease da análise com `CLIP_ANALYSIS_QUEUE_CAPACITY` (1–64, padrão 8), `CLIP_ANALYSIS_LEASE_SECONDS` (30–300, padrão 60) e `CLIP_ANALYSIS_DEFAULT_VERSION` (até 64 caracteres alfanuméricos, `-`, `_` ou `.`; padrão `analysis-v1`). O wrapper projeta `PLATFORM_CLIP_ANALYSIS_*`. Jobs/políticas residem no SQLite IAM já configurado; não há broker, worker/modelo de IA, retenção de jobs ou resultado de interpretação.
