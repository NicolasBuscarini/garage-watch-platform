# Arquitetura local — T01

Este documento complementa, sem substituir, a arquitetura compartilhada em `../../docs/arquitetura/`. O fluxo implementado T01 é HTTP loopback → middleware de correlação/erro → query MediatR → Application → Domain, com `Infrastructure` implementando a porta de leitura do perfil via ambiente do host. O schema de resposta é versionado em `contracts/system-profile-response.v1.schema.json`. Domain/Application não referenciam HTTP nem infraestrutura; Host traduz o protocolo e faz composição.

O use case de perfil é somente leitura; não há banco/cache distribuído/broker/modelo ou adaptador NAS ativo. T01-O acrescenta `OpenTelemetry` ao host: spans ASP.NET Core W3C e `use_case.execute`; métricas de execução/duração por caso de uso e meters ASP.NET/Kestrel/runtime .NET. Métricas customizadas usam tags estáticas `use_case` e `outcome`; não usam IDs por requisição, câmera/contexto, rota crua, texto da exceção nem payload. A correlação fica em logs/span tags, `trace_id`/`span_id` em escopo de log. OTLP HTTP-Protobuf (traces/métricas) só ativa com endpoint env válido; timeout e fila/lote do trace limitados; ausência/falha do backend não afeta resposta ou readiness. Headers de autenticação são injetados somente pelo ambiente protegido e nunca registrados. Exportação não é storage durável e nenhum dashboard/collector está incluído. O host dev roda em container loopback. T02 ativa apenas captura simulada por padrão, ou o adaptador FFmpeg quando selecionado; isso não homologa câmera, codec ou operação real. Inferência, NAS e capacidades seguintes continuam futuras.

T03 mantém painel estático same-origin, cookie HttpOnly/SameSite Strict e gateway HLS local. T03-IAM substitui credencial runtime única por bootstrap de primeira inicialização e ASP.NET Core Identity persistido em SQLite via EF Core migrations (`/data/identity/garagewatch.db`); senha é hash, lockout e papéis User/Viewer/Administrator são persistidos. Política local temporária ADR042 aceita senhas com mínimo de 6 caracteres sem composição obrigatória, inclusive números somente; login mantém lockout e rate limit, mas essa escolha reduz resistência a adivinhação e continua estritamente loopback. Código por e-mail/2FA não está implementado nem decidido. Persistência usa contratos de repositório tipado na Application, BaseRepository EF para consultas/paginação e `withDetails`, e UnitOfWork scoped que aplica transações no mesmo IamDbContext usado por Identity. Gate singleton serializa transações IAM dentro de uma instância do host; `DbContext` não é seguro para queries concorrentes e nenhuma coordenação entre hosts/processos é prometida. Grants são revogados, auditoria é append-only e UserManager/RoleManager continuam os owners de usuário/papéis; patch arbitrário/hard-delete/enable genérico são excluídos. T03-REG adiciona cadastro same-origin estritamente local: User ativa, sem e-mail/verificação/recuperação, sem grants, com resposta anti-enumeração, limite local e landing sem câmera. A política é exceção dev-only e não autoriza exposição LAN; UI/endpoints administrativos, pedidos de acesso e enforcement de grants por mídia continuam tarefas futuras. Alterações IAM atualizam SecurityStamp; cookie de 8 h é revalidado no máximo em 15 s; restart ainda invalida cookie pela chave Data Protection efêmera. Diretório/banco local são restritos ao usuário do serviço; volume local ignorado, sem backup/restore testado. Ambiente continua dev-only, loopback; não é autorização de produção nem liberação de LAN. Somente Viewer/Admin acessam monitoramento; User autentica sem receber câmera, e enforcement de concessões por mídia segue incompleto. T00-H/T12, CT02 e CT33 continuam pendentes.

T02 adiciona ao host um worker de captura independente do fluxo MediatR: `ISegmentCaptureAdapter` seleciona exatamente `synthetic` ou `ffmpeg-rtsp`; o adaptador FFmpeg segmenta RTSP/TCP em MPEG-TS, preserva timestamps dentro do epoch e ffprobe valida H.264 e, se `CAPTURE_AUDIO_ENABLED=true`, AAC. O spool local persiste o segmento combinado, manifesto versionado/checksum e lacunas com recuperação local. Vídeo é stream-copy; áudio é convertido em AAC mono 16 kHz/64 kbit/s. Cota de segmentos/tamanho e backoff são limitados. Health distingue liveness de readiness da captura e detalha somente nome/status do adaptador, epoch, contadores e código enumerado. O gateway HLS inclui discontinuity entre epochs. Contratos estão em `contracts/capture-segment-manifest.v1.schema.json` e `contracts/capture-gap.v1.schema.json`; limites e riscos em `docs/capture.md`. `bash scripts/verify-rtsp-contract.sh` exerce o adaptador via MediaMTX e publisher sintético H.264/AAC e verifica codecs/checksum e continuidade de timestamps; isso não é validação física. O spool é filesystem local de desenvolvimento, não banco, NAS, retenção de clipes ou garantia de fsync contra perda de energia.

T03-CAM-RES acrescenta watchdog de ausência de segmentos (`CAPTURE_SEGMENT_TIMEOUT_SECONDS`) ao worker, status `reconnecting` mantido até segmento persistido e counter de retries. `/api/v1/cameras` publica `streamEpoch` opaco; painel sobrepõe aviso acessível quando captura perde a fonte e recria HLS ao notar recuperação/novo epoch, tentando retomar se a pessoa já estava reproduzindo. Sem novo serviço, banco ou dependência. Validação limitada a fonte contratual e MediaMTX sintético; nenhum hardware/câmera real homologado.

T04A acrescenta `ClipTriggerWorker` no mesmo processo dev-only: a captura persiste segmento primeiro e tenta enfileirar seu manifesto em canal limitado; descarte por fila cheia é explícito e não faz a captura esperar. `FfmpegVisualChangeDetector` reduz um frame por segmento e compara delta/área ao frame anterior. Ao disparar, `LocalSegmentSpool` seleciona o pré-buffer, persiste manifesto `collecting`, protege os segmentos referenciados contra limpeza e agrega o pós-buffer; `LocalClipMediaAssembler` concatena os segmentos locais, produz thumbnail JPEG e checksums, depois marca `ready`. Manifestos sobrevivem restart e recuperam coleta ou expõem `lost_capacity`; mídia/análise permanecem separadas e este componente não chama runtime de IA. FFmpeg é uma fronteira externa injetada, com fake contratual apenas nos testes; não há banco, NAS, fila externa ou serviço novo.

T03-CAM-CATALOG adiciona ao SQLite IAM as entidades persistidas `CameraContext` e `CameraCatalogEntry`, com ID imutável, nome, estado enabled, versão otimista e timestamps UTC. Catálogo vazio é semeado no startup com `garage` e a câmera configurada em `CAPTURE_CAMERA_ID`; a migração não reescreve grants/histórico existentes. CRUD paginado Admin é same-origin nas mutações, versionado, auditado e usa desativação lógica. `/api/v1/cameras` deriva a coleção persistida, filtrando Viewer por grants ativos e estados enabled e revalidando o papel atual; URL RTSP, segredo e adaptador seguem fora do catálogo. Somente a câmera selecionada pelo worker pode reportar o estado de captura atual; itens adicionais não iniciam worker/HLS.

T03-USER-ADMIN adiciona `GET /api/v1/admin/users` (página máxima 100, filtro opcional `userId`) e detalhe sem e-mail, com papéis e concessões; `PUT .../{id}/roles`, `PUT/DELETE .../{id}/cameras/{cameraId}` e `DELETE .../{id}` (desativação lógica). Todo endpoint exige Administrator; mutações também exigem Origin same-origin. Operações usam os serviços tipados/UnitOfWork, preservam auditoria e invalidam SecurityStamp para revogar sessões; desativação também revoga as concessões ativas na mesma transação. Último Administrator permanece protegido. Grant resolve o contexto do catálogo e só permite câmera habilitada. O painel React mostra uma aba Admin acessível com paginação, detalhes expansíveis, papéis, grants e confirmação nativa da desativação; não expõe e-mail nem opera em sessão `User`.

T03-CAM-AUTH define `ICameraResourceAccess` como fronteira da Application, implementada sobre o SQLite IAM. Cada requisição a `/api/v1/cameras`, playlist e segmento consulta estado ativo/papel/grant e catálogo/contexto habilitados; não há cache. Admin pode ler mídia da câmera habilitada, Viewer somente com grant ativo, e User não pode acessar esses endpoints. Negação de mídia retorna 404 para não distinguir câmera/grant e gera auditoria mínima `camera.access.denied`; Range no segmento só é processado após autorização. Mudanças de grant também invalidam SecurityStamp. Testes HTTP cobrem Admin/Viewer/User, câmera não concedida/adulterada, grant concedido/revogado, Range e auditoria. O host não contém endpoints de eventos, clipes, exportação ou configuração por câmera; CT41 para esses recursos permanece pendente até existirem APIs reais. `./garage verify-platform` executa restore, verificação de formatação e testes Release via Compose.

T03-WEB mantém o código React independente em submodule Git `web/` e troca o webroot de runtime do Compose API para `/app/web`, preenchido por build multi-stage (Node fixado + `npm ci` + Vite). `web-dev` é profile loopback opcional com HMR e proxy Vite a `/api/*` e `/health/*`; o browser mantém origem/cookie da UI para a API e gateway HLS. Produção continua em um host/processo ASP.NET Core, sem serviço Node, CORS ou nova política de autenticação. A antiga UI estática em `src/GarageWatch.Api/wwwroot` foi removida após a revalidação de paridade; API e testes apontam explicitamente para `/app/web`, que contém somente o bundle do submodule. O repo frontend e os contratos/requisitos compartilhados documentam componentes, temas e testes. CT02 e inspeção real browser/device seguem pendentes.
